# 合规红线与自我约束

本工具包的定位是**个人研究、低频、公开数据**的采集。以下红线不是"建议"，是设计约束。

---

## 一、绝对红线

| # | 禁止 | 原因 |
|---|---|---|
| 1 | **不绕过硬付费墙** | 内容未下发到客户端即属访问控制，绕过等同越权。软付费墙（内容已在 DOM、仅被 CSS/JS 隐藏）只做 DOM 层揭示，不做服务端绕过 |
| 2 | **不提取凭据 / cookie / token / 密码** | 凭据属于用户与服务方之间的授权凭证，工具不应读取、存储或转发 |
| 3 | **不破解验证码** | 验证码是站点明确表达的"需要人类"意愿。工具检测到验证码时**停止并报告**，交由人工处理 |
| 4 | **不用于撞库、批量注册、刷量** | 属明确的滥用行为 |
| 5 | **不规避 robots.txt 的明示禁止** | 工具默认预检；`--no-robots` 仅在你确认有正当理由时使用 |

---

## 二、默认内置的自我保护

| 机制 | 默认值 | 作用 |
|---|---|---|
| robots.txt 预检 | **开启** | 抓取前先问站点是否允许 |
| 同域最小间隔 | **1.0s** | 不给服务器压力 |
| 请求抖动 | **±20%** | 避免形成可识别的规律性流量 |
| 失败指数退避 | `1s × 2^n`，上限 30s | 被限流时自动减速，而不是加大力度 |
| 退出码语义化 | `2` = 被拦需人工 | 不硬刚，把决定权交回人 |

**为什么"退避"比"重试轰炸"更符合站点利益**：站点限流表达的是"你太快了"。加大力度只会加速封禁，而减速往往能持续拿到数据。这是"符合各网站规定"最实际的落地方式。

---

## 三、抓取前的自检清单

- [ ] 数据是**公开可见**的吗？（不需要登录就能看到）
- [ ] `robots.txt` 允许吗？（工具会查，但你应该自己看一眼）
- [ ] 站点有公开的抓取政策 / API 吗？（有 API 就优先用 API）
- [ ] 我的频率会给站点造成压力吗？（默认 1s 是同域最小间隔）
- [ ] 数据用途是**个人研究**吗？
- [ ] 有没有更轻的替代方案？（RSS、官方 API、开放数据）

---

## 四、关于"绕过反爬"这件事的边界

本工具包做的是：**让自动化请求在站点看来更接近正常浏览器**。

它**不做**：破解加密参数、伪造身份、绕过访问控制、突破速率限制上限。

一条朴素但准确的判据：

> 如果你用浏览器手动访问、正常点击，能看到这些内容 —— 那么自动化拿到它，性质相同。
> 如果手动访问也看不到 —— 那自动化拿到它，就越界了。

---

## 五、风险披露

- 部分站点对自动化检测严格，**存在账号封禁风险**。工具内置了降低风险的措施（有头模式、真实 Chrome、限速、抖动），但**无法完全避免**。
- 使用 `--proxy` 时，**代理来源的合法性由使用者负责**。工具不提供、不推荐任何代理服务。
- 使用 T2 强指纹后端意味着**更强的伪装能力**，相应地也承担更高的合规责任。请仅用于你有权访问的公开数据。
- 部分后端有**许可约束**（例如 cloakbrowser 存在授权档位、camoufox 为 MPL-2.0），商用前请自行确认。

---

## 六、建议的采集姿态

1. **先找 API**。很多站点有公开 API 或 RSS，比抓页面稳定得多。
2. **从 T0 起步**。能直连就不要开浏览器 —— 既快又对站点压力小。
3. **只在必要时升级**。T2 是重武器，不是默认。
4. **低频、长期**优于**高频、一次抓完**。
5. **留下礼貌痕迹**。如果站点有 `Crawl-delay`，遵守它。
